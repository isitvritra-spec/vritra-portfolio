DTO between Services — bad practice?

Hey, it’s been a long that I haven't posted about optimization strategies in .NET for fast speed and basically a good case for FINTECH projects. Well, let’s talk about Data Transfer Objects

What Are DTOs, and Why Did We Love Them?

you’re building an ASP.NET Core API, and you need to send data from your business logic to the frontend without dragging along your entire domain model you must be using the DTO’s for that — simple, lightweight classes with just properties, no fuss, no muss means a minimalist backpackers of your application, carrying only what’s needed: a CustomerId, a Name, maybe an Email.

Back in the day, developers use DTOs a lot as they kept your layers decoupled, and let you custom data for specific endpoints, and made serialization a breeze. They were the glue between your database and your API, and we all sang their praises. But now its somewhat Messy!

🔹Issue with the DTOs

Now, let’s get real. DTOs are great until they’re not, and the “Death by DTO” is what happens when enthusiasm turns into excess. Here’s what I mean —

  • Performance: Every time you map your domain model to a DTO, you’re burning CPU cycles. Tools like AutoMapper are handy, but they’re not magic right? If you’re mapping thousands of objects in a high-traffic Fintech app, your server starts panicking. And don’t even think about nested DTOs — those are worse than the Daytime problem.
  • Codebase: Developers are too simple to understand and too complex to implement. So we create CustomerDTO, CustomerSummaryDTO, CustomerProfileDTO, and — why not? — CustomerUltraLiteDTO. With each exhibit differing by one property. Updating these when your domain model changes? That’s a full-time job, and nobody signed up for that.
  • Scalability Struggles: As your .NET application grows — say, a banking platform handling millions of transactions — those DTOs start piling up. This causes the overhead of mapping and serializing, which ultimately slows down your API, and your end users will see a loading screen. Not exactly the five-star experience you promised.
Remember, it’s about overusing DTO’s turn them into a liability.

🐈‍⬛DTOs Done Right (and Wrong)

The Wrong Way: DTO Overload

public class CustomerDTO
{
    public int Id { get; set; }
    public string Name { get; set; }
    public string Email { get; set; }
    public string Address { get; set; }
    public DateTime DateOfBirth { get; set; }
    public List<OrderDTO> Orders { get; set; } // Nested DTOs
    public string FavoriteCoffee { get; set; } // Because... why not?
}

public class OrderDTO
{
    public int OrderId { get; set; }
    public decimal Amount { get; set; }
    public DateTime OrderDate { get; set; }
}

This CustomerDTO is hauling around every piece of data, including the customer’s coffee preferences, for a simple endpoint that only needs a name and ID. Deploy this in a Fintech app handling real-time transactions, and you’ll have users debugging loading screen.

The Right Way: Keep It Simple, Smartie

public class CustomerSummaryDTO
{
    public int Id { get; set; }
    public string Name { get; set; }
}

This is the DTO equivalent of a well-packed carry-on. It’s lean, focused, and gets the job done without dragging your API through the mud. Use this for a dashboard displaying customer names

🤞Smarter Alternatives

So, how do we avoid this? Here are some of my strategies to keep your .NET app lean and mean:

  1. Instead of a DTO for every endpoint, create view models according to your specific use cases. If you need a customer list for a report then go for a CustomerReportViewModel.

2. Skip DTOs altogether with Entity Framework’s projection capabilities. For example:

var customers = await dbContext.Customers
    .Select(c => new { c.Id, c.Name })
    .ToListAsync();
This projects directly into an anonymous type or a minimal class, bypassing the DTO middleman. Your database query stays efficient, and your API responds smoothly

3. If you must use DTOs, keep them minimal.

Ask yourself, does this endpoint really need that property? If not, cut it.

4. And, use tools like BenchmarkDotNet to measure mapping overhead. If AutoMapper’s slowing you down, consider manual mapping for hotspots or explore faster libraries

These strategies are about building .NET apps that scale gracefully, whether you’re handling a few users or millions🪽

📈PROS and CONS of DTOs —

🔺

  1. DTOs keep your domain model separate from your API, reducing tight coupling.
  2. Customize data for specific consumers, like a mobile app or a third-party service.
  3. No business logic, just data — easy to serialize and send over the wire.

🔻

  1. Mapping and serialization can slow down high-traffic applications
  2. Multiple DTOs lead to redundancy and maintenance issues.
  3. Overuse bloats payloads, impacting response times as your app grows

Note that, for a Fintech app, where milliseconds matter and compliance audits loom, the cons can outweigh the pros if you’re not careful. Choose DTOs wisely, or they’ll shit on your codebase

As per my thoughts, when to Use (or Ditch) DTOs

— When to Use DTOs

  • Your API needs to expose a subset of data, like a customer’s name and balance for a mobile banking app.
  • You’re integrating with external systems that expect specific data shapes.
  • You want a clear separation between your domain and presentation layers in a complex system.

— When to Avoid DTOs

  • Your endpoint can use the domain model directly without exposing sensitive data.
  • Performance is critical, and mapping overhead is an issue(real-time trading platforms).
  • Your project is small, and DTOs add unnecessary complexity.

Conclusion

DTOs aren’t a bad thing by the way, but they’re not the good things either. They’re tools — handy when used right, shitty when overdone. So, go forth, slay those unnecessary DTOs and make good code!
