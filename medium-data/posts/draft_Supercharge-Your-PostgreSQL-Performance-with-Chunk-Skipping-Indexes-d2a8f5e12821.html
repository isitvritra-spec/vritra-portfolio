The Connection Between PostgreSQL Partitioning and Performance

Is your PostgreSQL database slowing to a crawl as your tables grow larger? You're not alone. Many database administrators turn to PostgreSQL partitioning as a solution. This technique divides massive tables into smaller, more manageable pieces called partitions, dramatically improving performance and efficiency.

Partitioning allows the database planner to access only the necessary partitions to satisfy a query, a process known as partition pruning. This approach is used in PostgreSQL's inheritance-based partitioning, declarative partitioning, and TimescaleDB's hypertables, which automatically partition your data into smaller chunks.

However, partitioning isn't a universal solution. If your queries don't filter by the partitioning column(s), you won't see any performance improvements. In fact, these queries can become painfully slow as PostgreSQL has to scan all partitions without being able to exclude any.

To address this limitation, TimescaleDB 2.16.0 introduces chunk-skipping indexes, enabling developers to dynamically prune and exclude partitions during query planning or execution. By defining these indexes on compressed hypertables for specific data types, you can achieve 7x faster performance with an 87% smaller storage footprint thanks to compression.

The Importance of Correlation in PostgreSQL Partitioning

Partitioning introduces a trade-off. Many use cases require queries that don't filter by the partitioning column. When this happens, PostgreSQL can't exclude partitions, resulting in slower, inefficient queries that scan all hypertable chunks.

However, secondary columns in these queries are often related to the partitioning column in some way—they're correlated. For example:

  • A job's end time typically follows its creation time by seconds or minutes
  • A satellite observation's database recording time follows the actual observation time
  • Sequential IDs and creation timestamps for the same entities increase synchronously

These correlations present an opportunity to optimize query performance beyond traditional partition pruning.

Introducing Chunk-Skipping Indexes

TimescaleDB's chunk-skipping indexes leverage these correlations to enhance query performance. Available in TimescaleDB 2.16.0, these indexes can be defined on columnar sections of hypertables for smallint, int, bigint, serial, bigserial, date, timestamp, and timestamptz columns.

Here's how to enable chunk-skipping indexes:

SELECT enable_chunk_skipping('your_hypertable', 'your_column');

Once enabled, TimescaleDB tracks the minimum and maximum values for the specified column in each chunk. During query execution, the database can exclude chunks where the query would find no relevant data, significantly improving performance.

Best practices for using chunk-skipping indexes include:

  • Enabling them on columns correlated with the partitioning column
  • Using them for columns frequently referenced in WHERE clauses
  • Adding them to multiple columns as needed for your workload

How Chunk-Skipping Indexes Work

Let's illustrate this with an example. Consider the following schema:

CREATE TABLE orders (
   order_id       serial, 
   time           timestamptz, 
   customer_id    int, 
   order_total    float
);

SELECT create_hypertable('orders', 'time', chunk_time_interval=>'1 day'::interval);

Without chunk-skipping indexes, a query like SELECT * FROM orders WHERE order_id = 3942785; would scan all 365 daily chunks, taking 2,177 milliseconds.

Creating a traditional index on order_id improves performance to 34.8 milliseconds, but increases storage requirements by 37%.

With chunk-skipping indexes and compression:

SELECT enable_chunk_skipping('orders', 'order_id');
ALTER TABLE orders SET (timescaledb.compress);
SELECT compress_chunk(show_chunks('orders'));
